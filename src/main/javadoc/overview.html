GenAI Client

GenAI Client is a Java library designed for seamless integration with Generative AI providers. It offers foundational prompt management and embedding capabilities, enabling AI-powered features across Machai modules. The library simplifies interactions with AI services, supporting semantic search, automated content generation, and intelligent project assembly within the Machanism ecosystem.

GenAI Client supports all types of project files, including source code, documentation, project site content, and other relevant files. Applications can expose project-specific capabilities as annotated tools, prompts, and resources; configure a provider; submit generation or embedding requests; and incorporate the results into project workflows.

Architecture

The provider package defines provider-neutral generation and embedding contracts and reusable infrastructure. It covers initialization and lifecycle behavior, instructions and prompts, function tools, prompt and resource handlers, project-directory context, type conversion, input logging, error handling, web search, MCP configuration, and usage integration. Implementations translate these contracts to backend SDKs while keeping vendor-specific configuration out of application code.

The implementation packages provide OpenAI and Anthropic adapters, route CodeMie- authenticated model requests to a compatible backend, execute local YAML-driven tools, and supply a disabled provider. Providers retain request state until cleared, so a reusable provider should be cleared before it is used for an unrelated conversation; implementations are not assumed to be safe for concurrent request construction.

The manager package resolves chat and embedding providers from provider-and-model identifiers and collects process-local input, cached-input, and output token-usage records. The tools package supplies runtime annotations and metadata for tools, prompts, resources, and parameters, together with service-based discovery, callable-tool contracts, compatibility filtering, conversation roles, and structured exception types. These relationships let host applications remain independent of vendor SDK details.

A typical integration resolves or constructs a provider, initializes it with a model and configuration, registers annotated function-tool objects, adds instructions or prompts, and performs a request. Embedding providers expose vector generation for semantic and similarity-based workflows.

Packages

org.machanism.machai.process.manager
Resolves configured generative-AI and embedding providers from provider-and-model identifiers and records usage by model identifier. Its central types are ProcessProviderManager, Usage, and UsageStatistics.
org.machanism.machai.process.provider
Defines provider-neutral generation and embedding contracts, reusable stateful provider behavior, delegation, type conversion, and logging for prompts, tools, resources, web search, and MCP server configuration.
org.machanism.machai.process.provider.impl
Supplies the no-operation provider and the deterministic YAML-driven tool provider, including local function discovery, invocation, serialization, and configurable tool-error behavior.
org.machanism.machai.process.tools
Provides runtime annotations and metadata for declaring Java tools, prompts, resources, and parameters, along with service-based discovery, compatibility filtering, callable-tool contracts, roles, and structured error types.
org.machanism.machai.ai.provider.impl
Implements OpenAI and Anthropic integrations, CodeMie authentication and model-prefix routing, backend-specific request translation, web search and MCP support, embeddings, and response-usage accounting.

Using the API

Start with the provider and tools package summaries to select a provider contract and declare application capabilities. Use the manager package when a provider must be selected dynamically from configuration. Concrete provider documentation describes backend-specific credentials, endpoints, model options, supported capabilities, and request lifecycle details. Register function-tool implementations when a model or local tool workflow needs access to project capabilities, and call the provider's clear operation before beginning an independent request on a reused instance.
